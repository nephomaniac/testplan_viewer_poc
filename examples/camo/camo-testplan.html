Verify CAMO Operator Deployment

Validate that CAMO operator is installed, running, and managed by OLM

beginner ⏱️ 10 minutes 🎯 80% hands-on 👁️ Read-Only
Safe to run - This test is read-only and makes no changes to the system

What You'll Learn

  • ✓ Verify CAMO operator is deployed and running
  • ✓ Check CSV (ClusterServiceVersion) status
  • ✓ Understand operator deployment patterns in OpenShift

📝 Steps

1
Verify CAMO deployment exists and is available
💡 Learning Note: Deployments manage the operator pod. An available deployment means the operator is running. 
oc get deployment configure-alertmanager-operator -n openshift-monitoring
Expected output: configure-alertmanager-operator 1/1 1 1
Why this step: Confirms the operator deployment exists and has the desired number of replicas running
🚨 Error: Error from server (NotFound): deployments.apps "configure-alertmanager-operator" not found
Solution: CAMO operator is not installed. Check if OLM has installed the operator or install manually.
Learn more: https://docs.openshift.com/container-platform/latest/operators/understanding/olm/olm-understanding-olm.html
2
Check CAMO pod is running
💡 Learning Note: The actual operator process runs inside a pod. Pod should be in Running state with no restarts. 
oc get pods -n openshift-monitoring -l name=configure-alertmanager-operator
Expected output: configure-alertmanager-operator-.* 1/1 Running
Why this step: Verifies the operator pod is healthy and not crash-looping
🚨 Error: Pod status shows CrashLoopBackOff
Solution: Check pod logs: oc logs -n openshift-monitoring deployment/configure-alertmanager-operator
3
Verify ClusterServiceVersion (CSV) exists and succeeded
💡 Learning Note: CSV is how OLM tracks operator installation. Succeeded status means OLM successfully installed and is managing the operator. 
oc get csv -n openshift-monitoring -l operators.coreos.com/configure-alertmanager-operator.openshift-monitoring
Expected output: configure-alertmanager-operator.* Succeeded
Why this step: Confirms OLM has successfully installed and is managing the CAMO operator

✅ Validation

Success Criteria:
  • ✓ Deployment shows 1/1 available replicas
  • ✓ Pod is in Running state with 1/1 containers ready
  • ✓ CSV phase is 'Succeeded'
What success means:

CAMO operator is installed, running, and being managed by OLM correctly

What failure means:

Operator is not installed, not running, or OLM is not managing it properly. Check OLM logs and CSV status.

🔧 Troubleshooting

Deployment exists but pod keeps restarting
Likely cause: Operator failing to start, likely due to RBAC issues or invalid configuration
Debug steps:
  1. Check pod logs: oc logs -n openshift-monitoring deployment/configure-alertmanager-operator
  2. Check for RBAC errors in logs
  3. Verify ServiceAccount exists: oc get sa configure-alertmanager-operator -n openshift-monitoring
Fix: Review logs for specific error, check RBAC permissions
Prevention: Ensure OLM has properly installed all RBAC resources

Read and Inspect Alertmanager Configuration

Read and inspect the current Alertmanager configuration managed by CAMO

beginner ⏱️ 15 minutes 🎯 70% hands-on 👁️ Read-Only
Safe to run - This test is read-only and makes no changes to the system

What You'll Learn

  • ✓ Understand how Alertmanager configuration is stored in Kubernetes
  • ✓ Learn to extract and read YAML from secrets
  • ✓ Identify receivers and routes in Alertmanager config

📝 Steps

1
Verify alertmanager-main secret exists
💡 Learning Note: Alertmanager configuration is stored in a Secret, not a ConfigMap. This allows Prometheus Operator to reload Alertmanager when config changes. 
oc get secret alertmanager-main -n openshift-monitoring
Expected output: alertmanager-main Opaque 1
Why this step: Confirms the secret exists before attempting to read it
2
Extract and display alertmanager.yaml from secret
💡 Learning Note: Secrets store data base64-encoded. The -o jsonpath extracts the alertmanager.yaml key and base64 decodes it. 
oc get secret alertmanager-main -n openshift-monitoring -o jsonpath='{.data.alertmanager\.yaml}' | base64 -d
Documentation Reference
Expected output: global:\n resolve_timeout:
Why this step: Retrieves the actual Alertmanager YAML configuration
3
List all receivers in the configuration
💡 Learning Note: Receivers define WHERE alerts are sent (PagerDuty, GoAlert, DMS, etc.). CAMO dynamically adds/removes receivers based on secrets. 
oc get secret alertmanager-main -n openshift-monitoring -o jsonpath='{.data.alertmanager\.yaml}' | base64 -d | yq eval '.receivers[].name' -
Expected output: null pagerduty goalert dms
Why this step: Shows which alert destinations are currently configured
4
Check if PagerDuty receiver exists
💡 Learning Note: If pd-secret exists, CAMO should have created a 'pagerduty' receiver. This command checks if it's present. 
oc get secret alertmanager-main -n openshift-monitoring -o jsonpath='{.data.alertmanager\.yaml}' | base64 -d | yq eval '.receivers[] | select(.name == "pagerduty")' -
Expected output: name: pagerduty
Why this step: Validates that CAMO configured PagerDuty routing if pd-secret exists

✅ Validation

Success Criteria:
  • ✓ alertmanager-main secret exists
  • ✓ alertmanager.yaml key is present and decodable
  • ✓ Configuration contains valid YAML
  • ✓ At minimum, 'null' receiver exists (default catch-all)
What success means:

Alertmanager configuration is present and readable

What failure means:

Secret is missing or corrupted. CAMO may not have reconciled yet or encountered errors.

Create PagerDuty Secret for Alert Routing

Create pd-secret and verify CAMO automatically adds PagerDuty receiver to Alertmanager configuration

intermediate ⏱️ 20 minutes 🎯 75% hands-on ⛓️ Depends on: 1 test(s) ✏️ Modifies State

⚠️ System Impact - Modifies State

⚠️ This test creates a PagerDuty secret that will cause CAMO to reconfigure Alertmanager. Alerts may start routing to the test PagerDuty key. Run cleanup test afterward to remove.

Impact:

Creates pd-secret in openshift-monitoring namespace, which triggers CAMO to reconfigure Alertmanager

Affected Resources:
  • • Secret: pd-secret in openshift-monitoring
  • • Secret: alertmanager-main (modified by CAMO)
Reversible: ✅ Yes
Persistence: permanent
Risk Level: medium
Safe to Retry: ✅ Yes
State Management
🧹 Cleanup Required: Run test test_cleanup_pagerduty_secret after completion to restore state
🚫 Production: This test should NOT be run in production environments

What You'll Learn

  • ✓ Understand how CAMO watches secrets to trigger reconciliation
  • ✓ Learn the structure of pd-secret and required keys
  • ✓ Observe automatic Alertmanager reconfiguration when secret is created

📝 Steps

1
Verify pd-secret does NOT exist (clean state)
💡 Learning Note: Before creating a secret, verify it doesn't already exist to ensure we're testing CAMO's create behavior. 
oc get secret pd-secret -n openshift-monitoring 2>&1
Expected output: Error from server (NotFound)
Why this step: Ensures clean starting state - if secret exists, delete it first or skip this test
2
Create pd-secret with test PagerDuty key
💡 Learning Note: CAMO looks for a secret named 'pd-secret' with key 'PAGERDUTY_KEY'. When created, CAMO's watch triggers reconciliation. 
oc create secret generic pd-secret --from-literal=PAGERDUTY_KEY=TEST_KEY_CHANGEME -n openshift-monitoring
Expected output: secret/pd-secret created
Why this step: Creates the secret that CAMO watches, triggering automatic Alertmanager reconfiguration
🚨 Error: Error from server (AlreadyExists): secrets "pd-secret" already exists
Solution: Secret already exists. Delete it first: oc delete secret pd-secret -n openshift-monitoring, or use --dry-run=client to test the command
🚨 Error: Error from server (Forbidden): secrets is forbidden
Solution: You lack permissions to create secrets in openshift-monitoring. Request cluster-admin role.
3
Wait for CAMO to reconcile (30-60 seconds)
💡 Learning Note: Operator watches are eventually consistent. CAMO needs time to detect the new secret, reconcile, and update alertmanager-main. 
sleep 60 && echo 'Reconciliation period complete'
Expected output: Reconciliation period complete
Why this step: Gives CAMO time to detect the secret and update Alertmanager configuration
4
Verify CAMO added PagerDuty receiver to Alertmanager config
💡 Learning Note: After reconciliation, alertmanager-main secret should now contain a 'pagerduty' receiver configured with the routing key from pd-secret. 
oc get secret alertmanager-main -n openshift-monitoring -o jsonpath='{.data.alertmanager\.yaml}' | base64 -d | yq eval '.receivers[] | select(.name == "pagerduty")' -
Expected output: name: pagerduty
Why this step: Confirms CAMO successfully added PagerDuty receiver to Alertmanager configuration
5
Check pd_secret_exists metric is 1
💡 Learning Note: CAMO exposes metrics for monitoring. pd_secret_exists should be 1 when pd-secret exists, 0 when absent. 
oc exec -n openshift-monitoring deployment/configure-alertmanager-operator -- curl -s localhost:8080/metrics | grep 'pd_secret_exists'
Expected output: pd_secret_exists 1
Why this step: Validates CAMO's internal state matches the actual secret presence

✅ Validation

Success Criteria:
  • ✓ pd-secret created successfully
  • ✓ Alertmanager config contains 'pagerduty' receiver
  • ✓ pd_secret_exists metric shows 1
  • ✓ No errors in CAMO operator logs
What success means:

CAMO successfully detected pd-secret and reconfigured Alertmanager to route alerts to PagerDuty

What failure means:

CAMO failed to reconcile. Check operator logs for errors. Secret may have wrong key name or CAMO may not have RBAC permissions.

🔧 Troubleshooting

Secret created but pagerduty receiver not in config after 2 minutes
Likely cause: CAMO reconciliation failed or operator is not running
Debug steps:
  1. Check CAMO pod is running: oc get pods -n openshift-monitoring -l name=configure-alertmanager-operator
  2. Check CAMO logs for errors: oc logs -n openshift-monitoring deployment/configure-alertmanager-operator --tail=50
  3. Verify secret has correct key: oc get secret pd-secret -n openshift-monitoring -o jsonpath='{.data.PAGERDUTY_KEY}'
Fix: Review logs for specific error, ensure secret has PAGERDUTY_KEY key (not pagerduty_key or other variations)
Prevention: Always check operator logs after creating secrets to confirm reconciliation succeeded
