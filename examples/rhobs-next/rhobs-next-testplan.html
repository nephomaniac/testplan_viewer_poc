⚠️ System Impact - Modifies State

Impact:

Read-only queries against Prometheus API. No modifications to cluster state.

Reversible: ✅ Yes
Persistence: none
Risk Level: minimal
Safe to Retry: ✅ Yes
State Management

What You'll Learn

  • ✓ Understand how blackbox-exporter generates probe metrics
  • ✓ Learn to query Prometheus using PromQL
  • ✓ Master interpretation of probe_success, probe_duration_seconds, and probe_http_status_code metrics
  • ✓ Understand metric labels and their role in filtering
  • ✓ Learn to access Prometheus via port-forward and API queries
⚠️ Common Beginner Mistakes
❌ Querying immediately after RouteMonitor creation
→ No metrics found because Prometheus hasn't scraped yet (default 30s interval)
✅ How to avoid: Wait at least 60 seconds after ServiceMonitor creation before querying metrics
❌ Not escaping curly braces in PromQL queries when using shell
→ Shell interprets braces as brace expansion, query fails
✅ How to avoid: Always quote PromQL queries: 'probe_success{job="console-route-monitor"}'
❌ Assuming probe_success=1 means healthy application
→ Probe succeeds but application returns 500 errors - check probe_http_status_code
✅ How to avoid: Always check both probe_success AND probe_http_status_code metrics
❌ Not filtering metrics by job or instance label
→ Query returns all probes, making results hard to interpret
✅ How to avoid: Use label filters: probe_success{job="console-route-monitor"} to scope to specific probe

1
Wait for operator reconciliation (The control loop process where a controller compares desired state (spec with actual state and takes actions to converge them
💡 Learning Note: Prometheus scrapes metrics at intervals defined in ServiceMonitor (typically 30s). After ServiceMonitor creation, Prometheus reloads its configuration (takes ~30s), then performs first scrape. Wait at least 90 seconds total to ensure metrics are available. This prevents false negatives from querying too early. 
echo 'Waiting 90 seconds for Prometheus to scrape metrics...' && sleep 90
Expected output: Waiting 90 seconds for Prometheus to scrape metrics... (90 second pause)

💡 Learning Note: Port-forwarding creates a local tunnel to a Kubernetes service, enabling local access without exposing the service externally. The -n openshift-monitoring flag specifies the namespace. Port 9090 is Prometheus's default web UI and API port. The & runs it in background. Keep this running for subsequent query steps. 
oc port-forward -n openshift-monitoring svc/prometheus-k8s 9090:9090 &
Expected output: Forwarding from 127.0.0.1:9090 -> 9090 Forwarding from [::1]:9090 -> 9090
🚨 Error: Unable to listen on port 9090: Listeners failed to create with the following errors: [unable to create listener: Error listen tcp4 127.0.0.1:9090: bind: address already in use]
Solution: Kill existing process: lsof -ti:9090 | xargs kill -9, or use different local port: oc port-forward -n openshift-monitoring svc/prometheus-k8s 9091:9090
🚨 Error: Error from server (NotFound): services "prometheus-k8s" not found
Solution: Find Prometheus service: oc get svc -A | grep prometheus
3
Verify Prometheus API accessible
💡 Learning Note: The /api/v1/query endpoint is Prometheus's instant query API. It evaluates PromQL (Prometheus Query Language - a functional query language for selecting and aggregating time-series data) [learn more](https://prometheus.io/docs/prometheus/latest/querying/basics/) expressions at a single point in time. The up metric is a built-in metric showing scrape success (1 = success, 0 = failure). Testing with 'up' confirms Prometheus is responding before querying probe-specific metrics. The jq tool formats JSON for readability. 
curl -s 'http://localhost:9090/api/v1/query?query=up' | jq .status
Expected output: "success"
🚨 Error: curl: (7) Failed to connect to localhost port 9090: Connection refused
Solution: Wait 5 seconds for port-forward to establish, then retry. Verify port-forward running: ps aux | grep port-forward
🚨 Error: jq: command not found
Solution: Install jq or omit | jq .status to see raw JSON output
4
Query probe metrics from Prometheus
💡 Learning Note: probe_success is a gauge metric exported by blackbox-exporter (A Prometheus exporter that performs HTTP, TCP, DNS, and ICMP probes and exposes their results as metrics) [learn more](https://github.com/prometheus/blackbox_exporter). Value 1 means probe succeeded (target responded), 0 means failed. The job label matches the ServiceMonitor name. The instance label shows the target URL being probed. This is the primary metric for alerting on probe failures. 
curl -s 'http://localhost:9090/api/v1/query?query=probe_success{job="console-route-monitor"}' | jq '.data.result[] | {metric: .metric, value: .value}'
Expected output: { "metric": { "job": "console-route-monitor", "instance": "https://console-openshift-console.apps.cluster.example.com", ... }, "value": [ 1676987654, "1" ] }
🚨 Error: "result": []
Solution: Verify ServiceMonitor exists: oc get servicemonitor -n openshift-route-monitor-operator. Check Prometheus targets: curl -s 'http://localhost:9090/api/v1/targets' | jq '.data.activeTargets[] | select(.labels.job=="console-route-monitor")'
🚨 Error: "value": [<timestamp>, "0"]
Solution: Check probe_http_status_code metric for details. Verify target URL is accessible: curl -I <target-url>
5
Query probe metrics from Prometheus
💡 Learning Note: probe_http_status_code shows the HTTP response code from the probe (200, 404, 500, etc.). This differentiates between different failure modes: 404=not found, 500=server error, 0=couldn't connect. Combined with probe_success, this provides detailed probe health insight.
